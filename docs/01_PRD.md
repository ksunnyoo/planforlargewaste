## 1. 문제 정의서 (Problem Statement)

### 1.1 대상과 상황
- 대상: 이사·정리 업체의 견적·상담 담당자(실장).
- 상황: 고객이 버릴 물건 목록을 보내면, 담당자가 해당 지자체의 대형폐기물 품목명·규격·수수료·신고 절차를 찾아 고객에게 안내합니다.

### 1.2 현재 방식의 한계
1. 고객이 쓰는 표현("3인용 소파", "책상")과 지자체 공식 품목명·규격이 달라 일일이 대조해야 합니다.
2. 지자체마다 신고·배출 방식이 달라 안내문을 매번 찾아 읽어야 합니다.
3. 지자체 배출 수수료와 업체의 운반·작업비가 섞여 설명되면 고객이 총비용을 오해할 수 있습니다.
4. 안내가 틀리면 고객 항의와 재작업으로 이어집니다. **[가설]**

> 참고: 성남시 안내에는 배출자용 신고 채널로 모바일 앱 '빼기'가 소개되어 있습니다. 본 서비스는 **업체 담당자가 견적·안내를 준비하는 도구**로 배출 신고 자체를 대행하지 않으므로 용도가 다릅니다. 다만 사용자층이 일부 겹칠 수 있어 인터뷰에서 이용 여부를 확인합니다.

### 1.3 Why AI (규칙 기반으로 안 되는가?)
| 구간 | 규칙 기반 | AI(LLM·RAG) |
|---|---|---|
| 수수료 계산 | 가능 (표 조회 + 곱셈) | 쓰지 않음. 코드가 계산 |
| 품목명 매칭 | 키워드 검색은 표현 차이("쇼파/소파", "3인용")에 약함 | 의미 기반 검색 + 후보 중 선택으로 보완 |
| 한 줄 입력에서 품목·수량 분리 | 정규식은 문장 변형에 약함 | 구조화 출력으로 분리 |
| 배출 절차 안내 | 안내문이 비정형 텍스트 | 근거 문단을 검색해 체크리스트로 정리 |

결론: **계산은 코드, 이해·검색·정리는 AI**로 역할을 나눕니다. 이 분리가 환각 위험을 줄이는 핵심 설계입니다.

## 2. 가설·검증 정의서

| 번호 | 가설 | 검증 방법 | 성공 기준 |
|---|---|---|---|
| H1 | AI가 고객 표현을 공식 품목에 연결해 주면 담당자의 조회 시간이 줄어든다 | 담당자 대상 시나리오 테스트 | 수동 조회 대비 시간 단축 |
| H2 | 품목 후보 + 사람 확인 구조가 완전 자동보다 신뢰를 높인다 | 확인 단계 유무 비교 인터뷰 | 담당자가 확인 단계를 유용하다고 응답 |
| H3 | 지자체 수수료와 업체 작업비를 분리해 보여주면 고객 설명이 쉬워진다 | 결과 화면 사용성 테스트 | 담당자가 그대로 고객에게 전달 가능하다고 응답 |
| H4 | 업체가 월 구독 또는 건별 과금에 지불 의사가 있다 | 업체 인터뷰 | 지불 의사 표현 (MVP에서는 결제 미구현) |

**MVP 범위(가설 검증용)**: 텍스트 입력, 품목 매칭 → 확인 → 계산 → 절차 안내 → 결과 공유. 지자체는 아래 3단계 지원 수준을 따릅니다.

| 지원 수준 | 제공 기능 | 대상 | 결과 화면 표시 |
|---|---|---|---|
| 1. 수수료 + 절차 안내 | 품목 매칭, 수수료 계산, 근거 인용 절차 안내 | 성남시(수수료는 조례 별표 PDF, 절차는 성남시 자원순환 안내 `data/raw/seongnam_procedure.md`) | 전체 기능 |
| 2. 수수료만 | 품목 매칭, 수수료 계산 | 전국 표준데이터(2026-11-13 확인: 143개 기관, 23,186행)에 있고 규격이 기재된 지자체(129개 기관은 규격 빈칸 없음, 14개 기관은 규격 전부 빈칸이라 아래 정제 원칙 적용). **성남시는 이 데이터에 없음** | "이 지역은 수수료만 제공합니다. 절차는 해당 지자체의 안내를 확인하십시오." |
| 3. 미지원 | 없음 | 데이터가 없는 지자체 | 선택 목록에서 제외 |

지자체별 안내문이 확보될 때마다 수준 2를 수준 1로 올립니다. 2수준 지자체는 데이터 품질(누락·표기 차이)이 성남시보다 덜 검증됐음을 안내문에 명시합니다.

**제약 조건**: 비용 0원(모든 서비스 무료 티어), 1인 개발, 약 40시간, 공공데이터 실제 항목·누락률 미검증.

## 3. 페르소나 **[가설]**

> 강의자료 원칙에 따르면 페르소나는 실제 사용자 5~10명의 리서치 데이터에 근거해야 합니다. 5일 일정에서는 불가능하므로 아래는 가설 페르소나이며, 11/16까지 업체 2~3곳 전화 인터뷰로 보정하고 결과를 이 절에 반영합니다.

### 3.1 주 페르소나: 박정훈 실장 (가상 인물)
| 항목 | 내용 |
|---|---|
| 프로필 | 40대, 중소 이사·정리 업체 견적 담당. 하루 여러 건 상담. IT 숙련도 보통(카카오톡·엑셀 사용) |
| 목표 | 상담 중 폐기물 비용과 절차를 바로 안내하고 견적을 확정한다 |
| 행동 패턴 | 고객이 사진·문자로 보낸 물건 목록을 보며 지자체 홈페이지에서 품목을 검색해 수수료를 합산한다 |
| Pain Points | ① 품목명·규격 대조 반복 ② 지자체별 절차 상이 ③ 수수료와 작업비 구분 설명의 어려움 ④ 안내 오류 시 항의 |
| 기대하는 도구 | 입력하면 바로 후보가 나오고, 틀린 것은 내가 고칠 수 있는 도구 |

### 3.2 보조 페르소나: 이서연 (가상 인물)
30대 직장인, 이사 예정. 버릴 물건의 비용과 신고 방법을 알고 싶지만 지자체 홈페이지 구조가 복잡합니다. 업체가 공유해 준 안내 링크를 열어 확인하는 최종 독자입니다.

### 3.3 페르소나 검증 계획
- 업체 2~3곳에 5개 질문을 통화로 확인: 한 건당 조회 시간, 가장 자주 틀리는 품목, 지자체별 절차 차이 체감, 수수료·작업비 구분 방식, 지불 의사.
- 결과는 `docs/research/` 에 요약 기록합니다.

## 5. 솔루션 컨셉

### 5.1 서비스 컨셉
한 줄로 입력한 물건 목록을 **공식 품목 후보로 연결**하고, 담당자가 **확정**하면 **수수료를 코드로 계산**하며, **근거가 붙은 배출 절차**를 고객용 안내서로 만들어 줍니다.

### 5.2 AI와 사람의 역할 분담 (HITL)
| 단계 | AI | 사람 |
|---|---|---|
| 입력 해석 | 품목·수량 분리 | 오타·누락 수정 |
| 품목 매칭 | 후보 3개 + 이유 제시 | **품목·규격 확정** |
| 수수료 | 관여하지 않음 | 확인 |
| 절차 안내 | 근거 문단 검색·요약 | 안내서 전달 전 검토 |
| 개선 | 피드백 수집 | 오류 제보 |

### 5.3 도입 전략
강의의 두 전략 중 MVP는 **전략 B(새 도구에서 학습)** 입니다. 업체가 이미 쓰는 접점은 카카오톡이므로, 사업성 검증 후 **전략 A(카카오 채널 안에 AI를 숨김)** 로 확장하는 것을 로드맵에 둡니다.

### 5.4 가치 제안
- 담당자: 조회·대조 시간 절감, 안내 오류 감소.
- 고객: 총비용과 절차를 한 화면에서 이해.
- 업체: 설명 품질의 일관성, 근거 기록.

### 5.5 사용자 플로우
```
지자체 선택 → 물건 목록 입력 → [AI] 품목 후보 매칭
→ [사람] 품목·규격 확정 → [코드] 수수료 계산
→ [AI] 배출 절차·체크리스트(근거 인용) → 결과 화면
→ 공유 링크 / 인쇄 → (선택) 피드백
```

## 7. 기능 명세

공통 오류 처리: 네트워크 오류 시 "재시도" 토스트, 입력 검증 실패 시 필드 아래 안내문을 표시합니다.

### F-02 물건 목록 자유 입력 (Must)
- 스토리: 담당자로서, 고객이 보낸 목록을 그대로 붙여 넣고 싶다. 그래야 따로 정리하지 않아도 됩니다.
- 입력 제한: 1~500자.
- AC
  - Given 입력창에 텍스트가 있고, When "분석" 버튼을 누르면, Then 품목 후보 화면으로 이동합니다.
  - Given 입력이 비어 있으면, When 제출하면, Then "버리실 물건을 한 줄에 하나씩 입력하십시오." 안내가 표시됩니다.
  - Given 500자를 초과하면, Then 제출이 막히고 글자 수가 표시됩니다.
- 예외: 주소·전화번호 등 개인정보 입력 금지 안내 문구를 입력창 아래에 표시합니다.

### F-03 AI 품목 매칭 (Must)
- 스토리: 담당자로서, 고객 표현이 공식 품목으로 연결되길 원합니다.
- AC
  - Given "3인용 소파, 책상, 의자 4개"가 입력되면, When 분석하면, Then 3개 줄(소파·책상·의자×4)이 생성되고 각 줄에 후보 최대 3개가 표시됩니다.
  - Given 후보 점수가 임계값 미만이면, Then 해당 줄은 "확인 필요"로 표시되고 자동 선택하지 않는다.
  - Given 어떤 후보도 없으면, Then "공식 품목을 찾지 못했습니다. 직접 검색하십시오."를 표시합니다.
- 예외: LLM 호출이 모두 실패하면 키워드 검색 결과만 후보로 제시하고 "AI 보조 없이 검색한 결과입니다" 배지를 표시합니다.

### F-04 품목·규격 확정 (Must)
- 스토리: 담당자로서, 최종 품목과 규격은 내가 정하고 싶다.
- AC
  - Given 후보 목록이 있고, When 후보를 선택하면, Then 해당 줄의 단가가 표시됩니다.
  - Given 줄이 하나라도 미확정이면, Then "견적 만들기" 버튼이 비활성화됩니다.
  - Given 후보 중 맞는 것이 없으면, When 검색창에 입력하면, Then 품목 검색 결과에서 직접 선택할 수 있다.

### F-05 수수료 계산 (Must)
- 규칙: 금액은 DB의 단가(원, 정수)에 수량을 곱해 합산합니다. LLM은 금액을 생성하지 않습니다.
- 면제 품목의 줄에는 "무상 방문 수거 대상일 수 있습니다. 배출일 3~4일 전 콜센터 1599-0903으로 예약하십시오."를 함께 표시합니다(근거: 성남시 자원순환 안내의 대형폐가전 무상 방문 수거 사업). 단, 면제 표기와 무상 수거 대상 품목의 완전 일치는 보장하지 않으므로 "일 수 있습니다"로 표기합니다.
- 수수료 유형(`fee_type`): `paid`(금액 있음), `free`(전국 데이터의 무료), `exempt`(성남시 기준표의 면제). `free`·`exempt`는 합계에 0원으로 계산하고 화면에는 "무료" 또는 "면제"로 표시합니다. 단가가 0원이라는 이유로 행을 제외하지 않습니다.
- AC
  - Given 확정 품목 단가 5,000원×2개, 10,000원×1개이면, Then 지자체 수수료 합계는 20,000원입니다.
  - Given 면제 품목(냉장고 등)과 5,000원 품목 1개씩이면, Then 지자체 수수료 합계는 5,000원이고 면제 품목 줄에는 "면제"가 표시됩니다.
  - Given 수량이 1~99 범위를 벗어나면, Then 검증 오류가 발생합니다.

### F-06 배출 절차·체크리스트 (Must)
- 스토리: 담당자와 고객으로서, 어떻게 신고하고 내놓는지 근거와 함께 알고 싶다.
- AC
  - Given 안내문 청크가 검색되면, Then 절차 단계마다 출처(문서명·구간)와 기준일이 인용됩니다.
  - Given 근거를 찾지 못하면, Then "해당 지자체 안내 확인 필요"를 표시하고 내용을 생성하지 않는다.

### F-07 결과 화면 (Must)
- 구성: ① 품목 표(품목·규격·수량·단가·소계) ② 지자체 수수료 합계 ③ 업체 작업비(입력 시) ④ 총 예상 금액 ⑤ 배출 절차·체크리스트 ⑥ 출처·기준일·면책.
- AC: Given 작업비가 입력되지 않았으면, Then 총액 대신 "지자체 수수료 합계"만 강조하고 "작업비는 업체에 문의" 안내를 표시합니다.

### F-08 기준일·출처·면책 (Must)
- 모든 결과 화면에 데이터 기준일, 출처 데이터 이름, "실제 수수료와 절차는 해당 지자체의 안내를 확인하십시오." 문구를 표시합니다.
- AC: Given 지원 수준 2 지자체의 견적이면, Then 절차 영역에 "이 지역은 수수료만 제공합니다. 절차는 해당 지자체의 안내를 확인하십시오."가 표시되고 절차 내용은 생성하지 않는다.

### F-09 공유 링크 / F-10 인쇄 (Should)
- AC: Given 결과가 저장되면, Then 짧은 공개 ID가 담긴 링크가 생성되고 30일 후 만료됩니다.
- AC: Given "인쇄" 버튼을 누르면, Then 인쇄 전용 스타일(A4, 버튼 숨김)로 열린다.

### F-11 피드백 (Should)
- 결과 화면에서 줄별 "품목이 틀렸습니다", 전체 "절차에 오류가 있습니다"를 보낼 수 있습니다. 개인정보 입력 금지 안내를 표시합니다.

### F-13 LLM 폴백·저하 모드 (Should)
- 순서: Gemini → Groq → (로컬 개발 환경에서만) Ollama. 모두 실패하면 저하 모드로 동작합니다.

### 8.3 가드레일
1. 금액·수량은 LLM 출력에서 받지 않고 DB·사용자 입력으로만 계산합니다.
2. 품목은 **후보 목록 안에서만** 선택하게 합니다(닫힌 집합).
3. 근거(청크)가 없으면 답을 생성하지 않고 "확인 필요"를 반환합니다.
4. 출력은 스키마 검증을 거치며 실패 시 1회 재시도 후 저하 모드로 전환합니다.
5. 개인정보(주소·연락처)는 수집하지 않으며 입력 시 마스킹 안내를 표시합니다.
6. 모든 화면에 기준일·출처·면책을 표시합니다.

### 8.4 UX와 피드백 루프
- 로딩: 단계별 진행 표시(해석 중 → 후보 검색 중 → 절차 정리 중)와 함께, LLM이 결과를 생성하는 동안 **스켈레톤 UI**(줄 카드·절차 패널 모양의 회색 자리표시)를 표시합니다.
- 서버 대기: 응답이 5초를 넘으면 서버 시작 안내 문구를 표시합니다(10.5절).
- 재생성: 절차 안내 다시 만들기 버튼(Should).
- 피드백: 줄별·전체 신고 → `feedback` 테이블 저장 → 평가셋 후보로 활용.
- 프론트 상태 관리: 화면 안의 임시 상태(입력 텍스트, 줄별 선택·수량, 진행 단계)는 **Zustand**, 서버 요청의 로딩·오류·재시도는 **TanStack Query**, HTTP 호출은 **axios** 인스턴스(타임아웃 25초, 공통 오류 형식 처리)로 담당합니다. 상세는 SDD 12절을 따릅니다.

## 10. UX·디자인 방향

### 10.1 취지에 맞는 톤
공공기관 안내문과 같은 **신뢰감과 명확성**을 우선하고, 친근함은 어투가 아니라 **시각 요소**(둥근 모서리, 여백, 따뜻한 배경색, 단순한 아이콘)로 만듭니다. 금액·출처·기준일 영역은 장식 없이 정돈된 표로 표시합니다. (사용자 결정, 2026-11-13: 해요체 대신 공공기관 어투)

### 10.2 디자인 토큰 (초안)
| 용도 | 값 |
|---|---|
| 주 색상 | 청록 계열 (예: #0F766E), 포인트색 1개 |
| 배경 | 따뜻한 밝은 회색 (예: #F8F7F4), 카드는 흰색 |
| 보조·텍스트 | 짙은 남색 (예: #0F172A), 회색 계열 |
| 상태색 | 확정 = 초록, 확인 필요 = 주황, 오류 = 빨강, 정보 = 파랑 (색 + 아이콘 + 짧은 문구를 함께 표시) |
| 서체 | Pretendard 또는 시스템 한글 폰트 스택 |
| 모서리·간격 | 카드 12~16px 모서리, 8px 배수 간격, 넉넉한 여백 |
| 아이콘 | 단순한 선형 아이콘 |

### 10.3 화면 목록
1. 입력 화면: 지자체 배지, 입력창, 개인정보 안내, 예시 입력.
2. 품목 확인 화면: 줄별 카드(원문, 후보 3개, 신뢰도 배지, 직접 검색).
3. 결과 화면: 견적 표, 합계 영역, 절차 체크리스트, 출처·기준일, 공유·인쇄 버튼.
4. 공유 보기 화면: 결과 화면의 읽기 전용 버전.
5. 소개·한계 안내(작은 푸터 또는 모달): 데이터 출처, 면책.

### 10.4 컴포넌트 (Atomic 구조)
Atom: Button, Input, Badge, Card, Skeleton. Molecule: ItemCandidateRow, FeeSummaryRow, ChecklistItem. Organism: ItemReviewList, EstimateTable, ProcedurePanel. Template·Page: InputPage, ReviewPage, ResultPage, SharedPage.

### 10.5 UI 문구 원칙
공공기관 안내문의 하십시오체(~합니다, ~하십시오)로 통일하고, 품목·절차 용어는 지자체 안내문의 표기를 그대로 사용합니다(예: 배출 신고, 수수료). 문장은 짧게 씁니다.

| 상황 | 문구 |
|---|---|
| 입력 안내 | 버리실 물건을 한 줄에 하나씩 입력하십시오. |
| 개인정보 | 주소와 연락처는 입력하지 마십시오. |
| 확인 필요 배지 | 확인이 필요합니다 |
| 로딩 | 품목을 분석하고 있습니다. 잠시 기다려 주십시오. |
| 서버 대기 | 서버를 시작하고 있습니다. 최대 1분 정도 걸릴 수 있습니다. |
| 근거 없음 | 해당 지자체 안내에서 확인되지 않습니다. 지자체에 문의하십시오. |
| 면책 | 실제 수수료와 절차는 해당 지자체의 안내를 확인하십시오. |

## 11. 수익모델·상업화 가설 **[가설]**
MVP에서는 결제를 구현하지 않고 아래 가설을 인터뷰로 검증합니다.

| 항목 | 가설 |
|---|---|
| 고객 | 이사·정리 업체 |
| 과금 | 업체 월 구독 + 안내서 건별 과금 |
| 검증 | 업체 인터뷰에서 월 지불 의향 구간 확인 |
| 확장 | 지자체별 절차 안내 추가(수수료는 전국 데이터 활용) → 업체 계정·팀 기능 → 카카오 채널 연동 → 사진 인식 |
| 비용 구조 | 현재는 무료 티어. 이용량 증가 시 LLM·DB·호스팅 비용이 발생하므로 단가 설계 시 반영 |
| 확인 필요 | 공공데이터 이용 허락 범위와 상업적 이용 조건 **[검증 필요]**, 개인정보·약관 정비 |
