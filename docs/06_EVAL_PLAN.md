## 1. 목적과 범위

- 목적: ① 품목 매칭과 절차 안내의 품질을 **숫자와 근거**로 보이고, ② 구성별 개선 효과를 비교하며, ③ 평가 과정을 **추적 가능한 기록**으로 남깁니다.
- 범위: 품목 매칭(검색·선택·판정·수량), 절차 RAG(인용·거절·충실도), 종단 결과와 응답 시간.
- 범위 밖: 수수료 계산의 정확성은 평가가 아니라 **단위 테스트**로 검증합니다(계산은 코드이므로 100%가 기준).
- 참고 저장소(grant-finder-rag)의 지표는 참조만 하며, 아래 설계로 확장합니다.

## 2. 평가 계층

| 계층 | 대상 | 질문 | 주요 지표 |
|---|---|---|---|
| L1 검색 | 후보 검색(trigram + 벡터 + RRF) | 정답 품목이 후보 안에 있는가, 얼마나 위에 있는가 | Recall@1/3/5, MRR, nDCG(등급 0/1/2) |
| L2 선택·판정 | LLM 후보 선택, 상태 판정, 수량 | 올바른 후보를 고르고 확실도를 맞게 판정하는가 | top-1 정확도, 상태 혼동행렬, 수량 정확도 |
| L3 절차 RAG | 절차 안내 생성 | 근거가 있고 충실하며, 근거가 없으면 거절하는가 | 인용 존재·유효, 거절 정확도, 오거절률, 충실도 |
| L4 종단 | 입력 → 견적 전체 | 최종 결과가 기대와 일치하고 시간 내인가 | 결과 일치율, 응답 시간 p50/p95 |

## 3. 평가셋 설계 (80문항)

### 3.1 구성
| 구분 | 문항 수 | 내용 |
|---|---|---|
| 매칭: 일상 표현 | 16 | "장롱", "침대 매트리스" 등 공식 명칭과 다른 표현 |
| 매칭: 오타·띄어쓰기 | 8 | "냉장꼬", "김치 냉장고" 등 |
| 매칭: 수량 표기 | 10 | "소파 2개", "의자 세 개" 등 |
| 매칭: 복수 규격 품목 | 10 | 규격 선택이 필요한 품목(기대 상태 ambiguous) |
| 매칭: 타 지자체 사례 | 8 | 수준 2 지자체의 품목명·규격 차이 |
| 매칭: 모호·미매칭 | 12 | 공식 품목이 없거나 판단 불가(기대 상태 unmatched/ambiguous) |
| **매칭 소계** | **64** | |
| 절차: 답변 가능 | 10 | 안내문에 근거가 있는 질문 |
| 절차: 답변 불가 | 4 | 안내문에 근거가 없는 질문(거절이 정답) |
| 절차: 수준 2 지자체 | 2 | 수수료만 제공하는 지자체(`unsupported`가 정답) |
| **절차 소계** | **16** | |

### 3.2 개발용·검증용 분리
- 구분(층)별로 비율을 맞춰 **개발용 70% / 검증용 30%** 로 나눕니다. 매칭 45/19, 절차 11/5, 합계 56/24.
- 개발용: 임계값·프롬프트·청킹 조정에 사용합니다. 검증용: **최종 측정 1회**에만 사용하며, 결과를 본 뒤 문항이나 설정을 고치면 이력에 기록하고 새 버전으로 올립니다.

### 3.3 문항 스키마(JSONL, 한 줄에 한 문항)
```json
{"case_id":"m-017","split":"dev","layer":"matching","category":"colloquial",
 "municipality_code":"3780000","input":"장롱 2개랑 매트리스 하나",
 "expected":[
   {"line":1,"gold_key":"3780000|장롱|<규격>","grade":2,"quantity":2,"status":"ambiguous"},
   {"line":2,"gold_key":"3780000|침대 매트리스|<규격>","grade":2,"quantity":1,"status":"ambiguous"}],
 "note":"작성자 메모"}
```
```json
{"case_id":"p-003","split":"test","layer":"procedure","municipality_code":"3780000",
 "question":"배출 신고는 어떻게 하나요?","answerable":true,
 "gold_sources":["성남시 자원순환 안내 '신고절차' 2단계"],"note":""}
```
- `gold_key`는 **지자체 코드 + 정규화한 품목명 + 규격**입니다(DB의 `item_id`는 재적재 시 바뀔 수 있으므로 쓰지 않습니다). 규격 칸은 실제 데이터 확인 후 채웁니다 **[검증 필요]**.
- `grade`: 2 = 정답, 1 = 허용 가능한 유사 품목, 0 = 오답(nDCG 계산용).
- 개인정보를 문항에 넣지 않습니다.

### 3.4 작성 규칙
- 실제 업체 입력을 가정한 문장과 피드백에서 온 사례를 섞습니다(피드백이 쌓이면 보강, 버전 상승).
- 한 문항에 정답 근거를 확인한 출처(데이터 행 또는 안내문 위치)를 `note`에 남깁니다.
- 작성자 한 명(1인 프로젝트)이므로 편향 가능성을 한계에 명시합니다.

## 4. 지표 정의

### 4.1 L1 검색
- **Recall@k**: 정답 품목이 상위 k개 후보 안에 있는 줄의 비율.
- **MRR**: 정답 순위의 역수 평균.
- **nDCG@k**: 등급(0/1/2) 기반 순위 품질.
- 구현은 ranx(개발 의존성)를 쓰되, 소규모이므로 직접 구현한 값과 일치하는지 한 번 교차 확인합니다.

### 4.2 L2 선택·판정
- **top-1 정확도**: 시스템이 선택한 1순위가 정답인 줄의 비율.
- **상태 혼동행렬**: 기대 상태(matched/ambiguous/unmatched)와 실제 상태의 3×3 표. 특히 *틀린 것을 matched로 단정*하는 오류(위험)와 *맞는 것을 ambiguous로 미루는* 오류(비용)를 분리해 봅니다.
- **수량 정확도**: 수량이 맞은 줄의 비율.

### 4.3 L3 절차 RAG
- **인용 존재율**: 절차 각 단계에 인용이 있는 비율(목표 100%).
- **인용 유효율**: 인용한 청크가 실제 존재하고 그 내용이 해당 단계를 뒷받침하는 비율(자동 검사 + 사람 확인).
- **거절 정확도**: 답변 불가 문항에서 `insufficient_evidence` 또는 `answerable:false`로 응답한 비율.
- **오거절률**: 답변 가능 문항에서 거절한 비율.
- **근거 충실도(Faithfulness)**: 답변의 각 주장이 인용 청크에 근거하는 비율. 답변 생성 모델과 **다른 모델**(예: Groq 계열)이 판정하고, 표본(예: 전체의 20%)은 사람이 확인해 판정기와의 일치도를 기록합니다. RAGAS 또는 DeepEval 사용은 개발 의존성으로만 하며 무료 모델 연동이 안 되면 직접 작성한 판정 프롬프트로 대체합니다 **[검증 필요]**.

### 4.4 L4 종단
- **결과 일치율**: 사람이 확정한 기대 품목·수량 기준으로 수수료 합계가 일치한 입력의 비율.
- **응답 시간**: p50, p95(첫 요청 지연 제외, 저하 모드 응답은 별도 표기).

## 5. 구성 비교 (ablation)

| 구성 | 내용 |
|---|---|
| C0 | trigram만 |
| C1 | 벡터만 |
| C2 | 하이브리드(RRF) |
| C3 | C2 + LLM 후보 선택 (기본 구성) |

각 구성에서 L1·L2 지표를 같은 평가셋으로 측정해 표로 비교합니다. C3가 C2보다 낫지 않으면 LLM 호출의 필요성을 재검토합니다.

## 6. 통계 처리
- 모든 지표에 **부트스트랩 95% 신뢰구간**(문항 단위 재표집, 예: 1,000회)을 붙입니다.
- 구성 간 비교는 같은 문항을 쓴 **짝지은 부트스트랩**으로 차이의 신뢰구간을 봅니다.
- LLM 비결정성: 각 구성을 **3회 반복**해 평균과 변동(최소·최대)을 기록합니다. 무료 한도 부담이 크면 C3와 최종 구성만 3회, 나머지는 1회로 줄입니다.
- 검증용 24문항(매칭 19)은 표본이 작아 신뢰구간이 넓습니다. 구성 간 작은 차이는 판별하지 못한다고 결과 문서에 명시합니다.

## 7. 실행 절차
1. 평가셋 파일과 버전을 고정하고 `CHANGELOG.md`에 기록합니다.
2. 시드·구성·모델명을 명시해 `run_eval.py --config C3 --split dev --repeat 3` 형태로 실행합니다(명령은 예시).
3. 결과 원본을 `eval/runs/`에 저장하고(8.2절), 지표와 신뢰구간을 계산합니다.
4. 개발용 결과로 조정 → 조정 사항을 평가 일지에 기록.
5. 조정이 끝나면 검증용으로 **최종 측정 1회**를 실행합니다.
6. 평가 일지에 해석(무엇이 잘 되고 어디서 틀렸는지, 오류 유형)과 후속 조치를 씁니다.
- 무료 한도: 평가 호출도 일일 LLM 한도를 소모하므로, 개발 중에는 Ollama(로컬)로 구조 점검을 하고 최종 측정만 Gemini/Groq로 실행합니다. 호출 수는 실행 전에 추정해 둡니다 **[검증 필요]**.

## 9. 한계 (결과 문서에 함께 기재)
- 평가셋이 작고(80문항) 작성자가 1인이라 대표성과 편향에 한계가 있습니다.
- 검증용 문항 수가 적어 신뢰구간이 넓고, 작은 차이는 판별하지 못합니다.
- LLM 판정(충실도)은 판정 모델의 한계를 가지며, 사람 표본 확인으로 보완합니다.
- 수준 2 지자체는 데이터 누락·표기 차이가 클 수 있어 별도 표기합니다 **[검증 필요]**.
- 무료 티어 한도와 모델 변경으로 재현성이 달라질 수 있어 모델명과 실행 일시를 기록합니다.

## 11. 미결·확인 필요
1. 수수료 데이터의 실제 규격 표기(gold_key의 규격 칸 작성에 필요).
2. 성남시 절차 안내 자료의 확보 방법과 형식(절차 문항의 출처 표기 방식). 성남시 수수료 gold_key는 별표 PDF(`data/processed/seongnam_fees.csv`) 기준으로 작성.
3. ranx, RAGAS/DeepEval의 버전과 무료 모델 연동 가능 여부.
4. 평가 호출량 대비 무료 한도 여유.
